# Инженерный план iPhone-пилота

Решение от 19 ноября 2026. Первый клиент — iPhone, минимальная целевая версия iOS 17. Один репозиторий для двух Mac. Первый испытатель — основатель. Личный профиль, архив оригиналов и уведомления работают на одном устройстве. Учебный профиль открывается отдельно. Серверная синхронизация, клиническая оценка и медицинские интеграции запланированы. Порядок запуска текущей версии приведён в [README](../../README.md). [Вся архитектура](architecture.md) · [Экраны](screens.md) · [Приёмка](delivery.md)

Открывать один .xcodeproj из репозитория. Для физического iPhone — выбрать свою команду подписи в Xcode и устройство. Учётные данные и сертификаты не коммитить. |

URLSession для API, Keychain для токенов, защищённые временные файлы для импорта. Локальный кэш для работы между запусками добавляем вместе с политикой удаления. |
| Инициатива | На первом физическом устройстве проверить локальное уведомление с разрешения пользователя. Для многопользовательского пилота — серверный планировщик и APNs. Ключ APNs остаётся у сервера. При отключённом канале вопрос доступен во входящих. Доставку проверяем на закрытом приложении и под Focus; факт отправки не равен прочтению. |

| Модели и знания | Один адаптер к выбранной модели, ограниченный вывод по JSON-схеме, версия модели/промпта, небольшой проверенный каталог правил. Сначала сравнить поставщиков на одинаковых русских документах и по цене за принятый факт. Провайдер, условия сохранения запросов и допустимый регион — отдельное решение до реальных документов. |

## Где будут данные каждого человека

Одна региональная PostgreSQL на среду, общий набор таблиц и отдельный patient_id на профиль. В первой версии один аккаунт владеет одним профилем. Будущие семейные профили и доступ врача требуют таблицы полномочий и отдельного согласия. Сервер выводит разрешённый patient_id из проверенной сессии. Присланный клиентом идентификатор не даёт права на чтение. Для зависимостей используем составные внешние ключи по владельцу и записи, ограничения уникальности внутри профиля и политики доступа строк. При пуле соединений контекст владельца выставляется только внутри транзакции. Роль приложения не владеет таблицами и не имеет BYPASSRLS. [PostgreSQL RLS](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)

| Что | Где | Пример ключей / способ удаления |
|---|---|---|
| Аккаунты, сессии, согласия, устройства | БД; секреты шифрования и сервисные ключи в отдельном хранилище секретов | account_id, patient_id, scope, revoked_at; отзыв блокирует новые операции и задания. |
| Оригиналы и файлы страниц | Закрытое объектное хранилище в том же разрешённом регионе | Случайный ключ объекта, привязка к patient_id в БД, хэш содержимого уникален внутри профиля. Вход по короткой ссылке только после проверки прав. Ключ без ФИО и диагноза. [Механизм ограниченных ссылок](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html) |
| Источники, фрагменты, факты и события | PostgreSQL: source, evidence, observation, topic, region_link | У фрагмента страница, координаты/цитата; у факта дата события, загрузки, единица, состояние проверки и версионные связи. Отзыв основания пересматривает все зависимые выводы. |
| Предложения, планы, сообщения, доставка | PostgreSQL: proposal, plan_item, message, contact, outbox, delivery_attempt | Атомарно записываем изменения и событие; worker обрабатывает их повторяемо. Один ключ на повод и версию действия, нейтральный текст push. |
| Публичные научные источники | Отдельный общий каталог rule_version, области применения и источники | Обновление утверждённой версии создаёт задания на проверку применимости внутри каждого разрешённого профиля. Личные данные не попадают в общий поисковый индекс. |
| Профиль для врача | Сначала генерируется на устройстве из выбранных подтверждённых данных | Экспорт помечен временем, оригиналы не прикладываются по умолчанию. Созданную пациентом внешнюю копию удалить из чужого устройства удалённо нельзя. |

**Где физически хранятся данные.** Личный архив и переписка находятся в контейнере iPhone. Приложение защищает файлы средствами iOS и исключает личные каталоги из резервного копирования. Экспортированным из приложения PDF распоряжается пользователь. Для будущей серверной версии выбираем площадку, обработчиков, политику резервирования и удаления с учётом рынка пилота. Решение для одной страны не переносится автоматически на другие. GitHub содержит исходный код и вымышленные примеры.

## Как попадает файл

| Вход | Первый планируемый приём | Что увидит человек |
|---|---|---|
| PDF выписки, анализа, ЭКГ с текстовым заключением | До 20 МБ и 30 страниц за файл в пилоте. PDFKit сначала ищет текстовый слой. Для сканированных страниц — OCR с координатами. | Имя, предполагаемая дата и тип; просмотр страницы, исправление спорного поля. Пароль, повреждение или превышение лимита дают явное объяснение. |
| Фото JPEG, PNG, HEIC с iPhone | До 10 МБ и 30 мегапикселей; проверяем декодирование, ориентацию, лимиты, нормализуем рабочую копию, исключаем лишние метаданные при передаче. | Можно переснять нечитаемое место. Если неясно, чей документ, запись остаётся на подтверждении. |
| Текст и дневник | Текст из диалога, ручное уточнение или выбранная порция данных Apple Health. Голос в первом выпуске — системная диктовка. | Происхождение «со слов пользователя», «из документа» или «из устройства» сохраняется навсегда для версии записи. |
| DICOM/КТ/МРТ-архивы, исходные кривые ЭКГ, ZIP, офисные файлы, видео | На первом этапе предложить приложить текстовое заключение в PDF/фото. Объёмные исследования потребуют отдельного импорта, просмотрщика и модели стоимости. | Принятые форматы и причина отказа до оплаты обработки. Автоматическая интерпретация изображений не входит в первый клинический сценарий. |

Численные ограничения выше — наши стартовые параметры. Конвейер: выбор → проверка формата по содержимому и квоты → разрешение загрузки → изолированный оригинал → проверка завершения и принадлежности → извлечение текста → кандидаты фактов → сверка цитат/единиц/дат → принятие или уточнение → новая версия плана, карты и уровня. Выделенные даты отличаем от даты печати и загрузки. Брошенный файл очищаем по сроку. При повторе того же файла у того же владельца возвращаем существующий источник; новую редакцию связываем с предыдущей. В реальном API сервер повторяет проверки клиента, сопоставляет контрольную сумму и допустимый размер, отдаёт статус разбора отдельно от результата. Таймаут модели не блокирует просмотр старого плана. Эти правила — спецификация импорта для блока 4.

## Как разные системы «советуются»

**Разбор одного человека.** Строим граф только из разрешённых источников: факты → эпизоды/темы/органы → вопросы/поручения. Орган — способ найти сведения, клиническая связь требует отдельного основания. Координатор формирует контекст по вопросу и периоду. Роль извлечения даёт факты и фрагменты, роль поиска подбирает подходящие версии рекомендаций, роль проверки ищет противоречия и исключения, аналитик собирает объяснение. Это четыре контракта, их может исполнять одна модель плюс обычный код. Любая модель получает минимальный контекст и не может сама записать назначение, открыть чужой профиль или рассылать сообщения.

**Пример решения.** В заключении одно поручение принести дневник. Записи дневника появились позднее, а в другой выписке указано, что дневник просмотрен. Проверяем, что это тот же вопрос и визит. При уверенной связи предлагаем закрыть дело, при неоднозначной — спросить «Это был тот же приём?». Сон из часов рядом по времени можно назвать наблюдением. Приписывать ему причину изменения показателя по одному совпадению нельзя.

**Формат ответа аналитика.** Указываем «что документировано», основания с версиями, «что пока неизвестно», конкурирующие объяснения, один вопрос/следующий шаг и кому он адресован. Для каждого дополнительного вопроса нужно показать, что меняет ответ «да», «нет» или «не знаю». Предпочитаем уже имеющийся материал и допускаем «ничего делать сейчас». Новую профилактическую рекомендацию для выбранной темы выпускаем после проверки врачом применимости, противопоказаний и сценария отказа. Нет основания — допускается только вопрос врачу. При исправлении/удалении материала пересматриваем и убираем устаревшие предложения и будущие отправки.

**Общий ресёрч.** Сначала узкая клиническая тема, утверждённые руководства с точным разделом, юрисдикцией, датой и условиями. Новые публикации попадают в очередь кандидатов, затем эксперт оценивает, изменилось ли правило. На контрольных вымышленных случаях проверяем пропуски, ложные срабатывания и необоснованные обследования. Включаем только одобренную версию, сохраняем возможность отзыва. Исследование данных разных людей — самостоятельный проект с отдельным основанием и условиями доступа. В данном пилоте общий только каталог знаний.

## Что получает врач

Без аккаунта в сервисе врач может прочитать сохранённый пациентом PDF. На первом экране — цель визита, период и выбранная область, подтверждённые факты с датами, происхождение, открытые вопросы и явно неизвестные сведения. Источник помечен номером страницы. В полноценном профиле добавим по подтверждённым данным лекарства/дозы, аллергии, заболевания, вмешательства, значимые результаты и семейную историю. Для неизвестного поля пишем «сведений нет»; отрицание требует собственного источника. В пилоте нет назначения лечения и печати врача на автоматически подготовленной сводке.

Общий вариант адресован терапевту. Передача специалисту начинает с того же профиля: например, выбрать «Сердце», проверить попавшие записи, при необходимости включить существенный контекст других систем, просмотреть и сохранить или показать на экране. До передачи оригиналов виден перечень и круг доступа. Позднее тестируем FHIR R4 / International Patient Summary, Composition, Bundle, Observation, DiagnosticReport, DocumentReference и Provenance с конкретной принимающей системой. Совместимость с клиникой заявляем только после проверки её профилей и реального импорта. [HL7 International Patient Summary](https://hl7.org/fhir/uv/ips/)

## Карта реализации

Календарная гипотеза при 20–25 часах разработки в неделю одним основателем с ИИ. Даты привязаны к 19.11.2026; отдых, подпись, клиническая и правовая проверка могут сдвинуть их. Это порядок зависимостей и показываемые результаты. Каждую неделю отмечаем фактические часы и перепланируем следующий блок. Внешнюю когорту начинаем только при готовой инфраструктуре и отрецензированном объёме.

| Окно | Блок | Результат, который можно проверить |
|---|---|---|
